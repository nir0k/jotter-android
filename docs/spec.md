# Jotter for Android — product specification

Jotter for Android is the mobile client of [Jotter](https://github.com/nir0k/Jotter), a note manager whose notes are stored as ordinary HTML files in a library folder. The Android client opens the same libraries, edits notes with the same rich text vocabulary and synchronises with the same sync storages as the desktop application, so a library moves between a phone and a computer without conversion.

## 1. Background and goals

The desktop application defines the library format, the features and the synchronisation model in its [product specification](https://github.com/nir0k/Jotter/blob/main/docs/spec.md) (the desktop specification below). This document specifies what the Android client does and how it does it on a phone; where it says "as on the desktop", the named section of the desktop specification applies unchanged.

Goals:

- Full parity with the desktop application for notes: read and edit every form of the note vocabulary (desktop specification section 3.3), including tables, code blocks, numbering styles, nested lists, images and attachments.
- Organise notes into collections, tags, favourites, the archive and the trash; file them by rules; find them by a scoped search with word forms in English and Russian.
- Capture notes from anywhere on the phone: an app shortcut, a Quick Settings tile and the system share sheet.
- Synchronise the library with an SFTP folder by the desktop's model (desktop specification section 12), so a phone and computers share one library.
- Export notes to PDF, HTML and JPG.
- Speak English and Russian, with the design system's palettes, Monokai, light and dark modes.

Non-goals:

- No library format of its own and no changes to the format made here. The format is changed in the desktop specification first; both clients then follow it.
- No library in folders shared with other applications (no Storage Access Framework library, no folder synchronised by other tools): the library lives in the application's private storage and reaches other devices only through Jotter's synchronisation (section 3).
- No ssh-agent and no `~/.ssh/config`, which do not exist on Android.
- No Google Play services or other proprietary dependencies, so the application can be built from source and published outside Google Play.
- No collaboration between people and no real-time co-editing, as on the desktop.

## 2. Relation to the desktop specification

- Terminology is that of the desktop specification (section 2): library, note, body, collection, tag, rule, favourite, archive, trash, geotag, attachment, note link, backlink, numbering style, index, sync storage.
- Normative for the Android client: the library format (section 3) and synchronisation (section 12) of the desktop specification. Notes, tags, collections, rules, search, the editor, export and the keyboard shortcuts of hardware keyboards behave as in the desktop application; this document names where the phone differs.
- The Android client implements library format 1 and note format 1. A library or a note of a newer format opens read-only with a notice asking to update Jotter, as on the desktop.
- Where this document describes Android behaviour differently, this document applies to the Android client only. A decision here that affects the format or synchronisation is a change of the desktop specification and is made there first.
- The client is tested against the library fixtures in `core/src/test/resources/fixtures/` (described in its `README.md`): library files covering the whole note vocabulary, which must read and write back byte for byte, and the merge cases of synchronisation (`merge/`: the base, local and remote versions of note, collection, rule and library files and the merged result), which must merge to the same bytes. The multi-step scenarios of the desktop's sync tests (two devices, the lock, deletions, the first connection) are ported as tests of their own with the same names and meaning, as data would need a language of their own to describe them.
- The fixtures are this project's own. They were written by the desktop application, so their bytes are what the desktop writes, and they are the reference for anything the desktop specification leaves open, such as the order of JSON keys or where the editor puts an empty paragraph. A fixture is changed or added only in the form the desktop writes, and a change of the library format or of synchronisation reaches them only after the desktop specification has made it.
- A note body is checked against the vocabulary (desktop specification section 3.3) whenever a note is read or written, by the same rules as the desktop's `bodyProblem`. Unknown elements, unsupported attributes and structural forms make the file malformed: it is listed under Problems and is never rewritten, by autosave, metadata changes or anything else. Unknown values of data attributes (numbering styles, colour keys, code languages) stay supported and round-trip. Present values of the wrong type in `library.json`, `collections.json` or `rules.json` are malformed too, never empty lists or default settings.
- A normalised copy is made only on request, from Problems in the Library tab of Settings after a confirmation: a new note with its own attachments, in the form the editor's codec writes, filed by the rules as a new note. The original stays byte for byte and stays under Problems until the person deletes it there with Delete original, confirmed, as a permanent deletion of the note: its file and attachment folder go and a tombstone takes the deletion to the other devices. The desktop reaches the file through its folder; a library on the phone is private storage, so this client offers the deletion itself. The codec lives in `core`, so the copy is written without the editor.
- Library files are never read or listed through symbolic links, and a symbolic link or special file among them is not synchronised: as a note file it shows under Problems, and it stops a sync run. A folder that cannot be listed stops the operation and never stands for an empty one. Attachment addresses whose parts hold a path separator, NUL or a dot path are refused. Unlike the desktop, which holds a directory descriptor for each path, the JVM offers no `openat`, so the last component and each listed folder are checked without following links; that is enough for the application's private storage, which only this application writes.

## 3. Library on the device

- The library lives in the application's private storage, `files/libraries/<library-id>/`, in the layout of the desktop specification section 3.2. Other applications cannot read it.
- One library is open at a time; the device preferences remember which. A new library is created in a temporary folder and moved under its identifier, so a failed creation leaves nothing behind; the temporary folders of a creation or download the system stopped half way are removed when the application next starts. The index is scanned when the library opens and whenever the application returns to the foreground. The Libraries screen of Settings creates a library, switches between the libraries on the device and deletes a library from the device (confirmed with the note count; copies on sync storages stay); the Sync tab of Settings downloads one from a sync storage.
- A library without a sync storage exists only on this phone. The first start and the Library tab of Settings say so, and the Sync tab offers to connect a sync storage.
- All application data is excluded from Android's cloud backup and device-to-device transfer: the sync storage is the second copy, a library restored from a stale backup would conflict with it, the credentials are encrypted with a Keystore key that does not move to another device, and settings restored without them would hold a connection that cannot sign in. The manifest disables backup and the data extraction rules exclude every domain explicitly.
- Every write is atomic: a temporary file in the same folder is written, flushed to disk and renamed over the target. A failed write keeps the text in the editor and shows the error next to the note.
- The index (desktop specification section 3.8) is an SQLite database in the application's no-backup folder, derived from the library and rebuilt when missing, outdated or on Rebuild index in the ⋮ of the Libraries screen. Search matches word forms of English and Russian through the Snowball stemmers, as on the desktop. The index is a device file and need not match the desktop's schema. As the platform SQLite has no FTS5 and accepts no custom tokenizers, the index uses the SQLite bundled by `androidx.sqlite:sqlite-bundled`, and `core` stems every word itself with the Snowball stemmers (generated Java, vendored in `core`) and the desktop's rules before writing it: the full-text table is contentless (`contentless_delete=1`) and holds only the stems, split on spaces by the `ascii` tokenizer, while the plain text is stored once in the notes table. Queries are stemmed the same way, so every word form matches as on the desktop. The fragments of search results are built in `core` from the matching words, as the desktop's `snippet()` shows them: up to 24 words around the first matches, with an ellipsis where the text goes on.
- The generated table of contents, `index.html`, is written as on the desktop (section 3.6), so the folder on a sync storage stays readable whichever device synchronised last: built three seconds after the last change of the notes (a scan, a sync run or a write of the application, collections included) or of the interface language, whose headings and short dates it uses, and written only when its contents changed, never in a read-only library. Writing it starts no sync run; the file goes to the sync storage with the next one.
- Unreferenced attachments are removed after 30 days and trashed notes after the library's retention period, as on the desktop (desktop specification section 3.5); the checks run when the application starts and once a day in the background (a periodic WorkManager job), after a scan of the index, and leave a read-only library alone. The index keeps the files each note refers to (`note_files`) and since when a file of an attachment folder is referenced by none (`unreferenced`, device state; losing the index only delays a removal); the folder of a note whose file cannot be read is left alone, and a folder left empty goes too. Every permanent deletion, an empty note discarded when it is left included, records a tombstone and drops the note's favourite (desktop specification section 3.2).
- Device files:

| File | Location | Content |
| --- | --- | --- |
| Libraries | `files/libraries/<library-id>/` | The libraries on this device. |
| Index | `no_backup/index/<library-id>.sqlite` | As on the desktop. |
| Settings | DataStore in `files/datastore/` | Device preferences, the open library, each library's sync connection and preferences. |
| Sync state | `no_backup/sync/<library-id>/state.sqlite` | As on the desktop (section 12.2), with content hashes in hexadecimal, plus the log of the five most recent runs shown on the Sync tab of Settings (section 8.1): the time, the files uploaded, downloaded, merged and deleted and the conflict copies, or the error; an older entry is removed when a run is added, and a run waiting for another device's lock is not logged. |
| Credentials | `no_backup/credentials/<library-id>.bin` | Passwords, key passphrases and private keys, encrypted (section 7.2). |
| Host keys | `no_backup/known_hosts` | SFTP host keys the person accepted. |
| Sync settings | DataStore, key `sync_<library-id>` | The library's connection (host, port, user name, folder, sign-in method, the public key of a key sign-in), the interval, what runs do on metered networks, the end of a pause and the time of the last successful run. |

## 4. Notes and organisation

Notes and their organisation behave as in the desktop application; this section names what differs on a phone.

- **Note list:** sorting by updated time, creation time or title, ascending or descending, as one device preference, chosen in a row above the notes (Favourites keep their own order). Each row shows the icon, the title in the note's colour ("Untitled" when empty), the date (updated or created, following the order; the time for today), up to two lines of the start of the text and the tags in their colours, a tag without a colour of its own taking its parent's. Titles and glyphs in a colour mix it 65% with the palette's text colour, as the desktop's titles and the design system's tag pills, so every colour stays readable in dark palettes. Rows open their note.
- **Selection:** a long press on a note starts selection in every note list of an editable library; further taps add or remove notes, Back clears it, and selected notes that leave the list leave the selection. The design system's selection bar replaces the bottom area: Clear, the count, Select all, the favourite toggle and ⋮ with Add to collection, Remove from this collection (in a collection's list), Add tag, Export, Archive and Move to trash; in the archive Unarchive, Export and Move to trash; in the trash Restore and Delete permanently (confirmed with the count). Archive, Unarchive, Move to trash and Restore show a snackbar with the count and Undo, which gives the notes back the collections, tags, archive and trash they had.
- **Favourites:** a note's or collection's menu adds or removes it, and the selection bar's toggle does so for the selected notes. In Favourites each favourite collection and note carries a drag handle; a row moves among the rows of its kind and is dropped in place of the row under its centre, and the other favourites keep their order in `library.json`, so the desktop's sidebar keeps its own.
- **Archive and trash:** as on the desktop. Archive and Move to trash from a note's menu close the note and show the snackbar with Undo in the list; Unarchive and Restore keep it open, now editable. Move to trash is not confirmed; Empty trash (in the trash's ⋮ while it holds notes) and Delete permanently are confirmed with the count.
- **Note's look:** Icon and Colour in a note's menu choose its icon from the icon picker's 120 glyphs in twelve groups (or No icon) and the colour of its title from the tag colours or a custom colour, applied at once. A note or collection shows the glyph of the name it stores when the desktop's icon manifest has it, not only the picker's, as a note from the desktop may store any of them (desktop specification section 3.9); the manifest's names are copied into `ui/src/main/resources/desktop-icon-names.txt`. Any other name, such as one a later release removed or one the design system keeps only for other products, shows no icon (a collection shows `Folder`), and the stored name is kept unchanged.
- **Collections:** the collection tree with expand and collapse; Add on the Collections destination creates a top-level collection. A collection's ⋮ offers New subcollection, Rename, Icon, Colour, Move (a dialog choosing the new parent, the top level or a collection outside its subtree, and the position among the new siblings, as dragging a tree is unreliable on a touch screen), Favourite, New rule (the rule form with the collection as its target) and Delete (confirmed with the number of subcollections and notes, with the desktop's option to move to the trash the notes left in no collection). Names are saved through form dialogs that keep their error. A collection with subcollections offers Only its own notes above its list, a filter chip remembered per collection on the device, as on the desktop.
- **Tags:** the tag tree with colours (section 5 of the desktop specification); a tag's ⋮ offers Rename (the last part of the path in a form dialog; a typed `/` nests it deeper; the tag and its children are renamed in every note, merged with an existing tag of the new name, and a snackbar tells in how many notes), Colour and Delete (confirmed with the number of notes). A note's tags are edited in a popup from the line under its title (section 8.1) and shown there, in its information and in the note lists; selected notes get tags from a dialog that searches the library's tags and creates new ones; `#word` in the body is ordinary text, as on the desktop.
- **Rules:** rules file notes by their tags only, as on the desktop: the conditions are Has the tag (the tag or its children, compared without case) and Has no tags, joined by All or Any, with the desktop's actions (Add to collections, Move to a collection) and Stop after this rule. Rules act as on the desktop when a note is created and when its tags change by any means (the Tags dialog, the selection, renaming or deleting a tag), and only when the note starts matching; a change of the title, a conflict copy and a sync run never run them. A rule of an earlier version with other conditions (on the title or with a regular expression) is listed with a notice that its conditions are no longer supported: it is never run or applied and cannot be edited, but can be switched, moved and deleted, and its conditions stay in `rules.json`; `caseSensitive` is kept as an unknown field and is not written to other rules. The Rules screen (the Library tab of Settings) lists the rules in their order, each with its switch, name and summary (conditions, what it does, Stop, or a deleted collection); tapping one opens its full-screen form, and its ⋮ offers Move up, Move down, Apply to existing notes (confirmed with the number of notes whose collections it changes, whether or not the rule is on; archived and trashed notes are skipped) and Delete (confirmed). A change made by rules is announced with Undo, which gives the notes back the collections they had: on the note's screen for a note being edited or just created (Undo goes through the editor's own write), in the list for changes made from a list, and on the Rules screen for Apply to existing notes.
- **Search:** as on the desktop. The search button of the home screen searches all notes, and that of a note list (all notes, unfiled notes, favourites, the archive, the trash, a collection's or a tag's notes) searches that list's view; each keeps its own query and filters while it is covered and across rotation. The button opens the search window (section 8.1), which holds the field, the filter toggle and the results; the filters are Search in (title, text, tags, collection names), Created and Updated (ranges of whole days in local time with both ends included), Collections and Tags (any of the chosen, with descendants and children), With attachments, With geotag, Search everywhere (outside all notes, the archive and the trash) and Include archived (outside the archive and the trash), and Clear while a filter is applied, wrapped on as many lines as they need; the filter toggle shows a dot while a filter is applied. A search runs 150 ms after its last change; results are ranked by relevance and show the fragment of their text with the matching words in bold. No matches is a state of its own with Clear search, which clears the query and the filters. The results are not selected: notes are selected in the lists themselves.
- **Unfiled notes:** the Unfiled notes list holds every active note in no collection. It is worked out from the note's collections and stores nothing: a note leaves the list when it is added to a collection, by hand or by a rule, and returns when it leaves its last one. Its round Add button creates an ordinary note.
- **Capture:** a note is captured from the application shortcut New note, the Quick Settings tile New note (after unlocking a locked phone, and added to the panel by the person) or the system share sheet, and opens in the capture screen: the note alone in the editor (title, body and formatting bar), without the home screen. Shared content opens it over the sharing application, so Back returns there; the shortcut and the tile open it in a task of its own, outside the recent screens, and Back returns where the person was. It is a second screen of the same application, sharing the open library with the main screen, which stays as it was; a link to another note opens that note in the main screen. A shared subject (such as a web page's title) becomes the title; each line of shared text a paragraph, with `http(s)` addresses as links; shared files (`content:` addresses only, so no application can hand over a file of Jotter's private folders by its path; of Jotter's own `FileProvider`, which Jotter could read although the sender cannot, only an attachment of the open library, as shared from Jotter itself, so no application can make Jotter copy a file of another library to this library's sync storage) are copied into the note's folder one by one, with a progress indicator naming how many are done, and follow the text in one paragraph as the editor inserts them: images recognised by their bytes, other files as attachments, up to 50 MB each; a file that cannot be added is named in a message on the note. The body is written in the desktop's form, so the editor does not rewrite it. Leaving while files are copied removes them and creates nothing. Without a library, or with one of a newer format, nothing is created: the screen says so with Open Jotter. A captured note gets a geotag when they are on and is filed by the rules, announced with Undo; otherwise it is among the unfiled notes.
- **Geotags:** Add location to new notes in the General tab of Settings, a device preference off by default. Turning it on asks for the location permission (precise and approximate together; the person may grant the approximate one, and the accuracy the phone reports is stored); a refusal leaves it off, and a permission withdrawn later shows it off. A new note, a captured one included, then asks the platform's location service for the current position (`LocationManager.getCurrentLocation` with the fused provider, otherwise the network or GPS provider; no Google Play services) and stores it rounded to five decimals with its accuracy and the time; a position not found within ten seconds is skipped, and the information sheet says so until the application restarts. The position arrives while the note is already open: the note's editor saves it with its own write, so it never counts as an outside change; a note left before then gets it in its file, unless it was discarded as empty. While the preference is on, the note's ⋮ offers Add location for a note without one; the information sheet shows the geotag with the design system's map and Copy actions and Remove location. Existing geotags stay visible and removable with the preference off.
- **Links between notes:** typing `[[` outside a code block opens the note picker (a dialog with a search field): with nothing typed it lists the 30 most recently updated notes, otherwise the notes whose titles match in any word form, archived ones included; the trash and the open note are never offered. Choosing a note replaces the brackets with a link showing the note's title; leaving the picker keeps the brackets. Note link in the insert menu opens the same picker at the cursor, and the link dialog has Note…, which puts the chosen note's address in (and its title as the text when the link has none). A note link opens its note, a trashed one read-only in the trash; a link whose note no longer exists is drawn muted and struck through and says "Note not found" when opened. Renaming a note renames the links in other notes that still show its old title, in the trash too; links with their own text keep it, as on the desktop. The index keeps the links of each note (`note_links`, since schema version 2; version 3 adds the attachment files of section 3).
- **Note information:** Information in the note's ⋮ opens a bottom sheet with the created and updated times, the collections and tags, the words, characters and attached files of the body as the editor holds it (counted as on the desktop: a word is a run of letters, digits and apostrophes, characters are UTF-16 code units without line breaks, a file shown twice counts once), the geotag and the backlinks outside the trash, each opening its note.

## 5. Editor

### 5.1 Vocabulary and engine

- The editor reads and writes every form of the note vocabulary (desktop specification section 3.3) and keeps what it does not change byte for byte, so a note edited on the phone reads back unchanged on the desktop except for the edit.
- The editor is native: Jetpack Compose text fields over a model of the desktop's document in `core`, the same model the body codec reads and writes, so the editor holds exactly the note vocabulary and every edit is a change of that model. Each run of blocks — the blocks of the root between two frames, or the blocks of a table cell — is one text field: its text is the blocks' text joined by a paragraph separator (U+2029), at which the field breaks the line and each block takes its own paragraph style, with line breaks inside a block as line feeds and images and chips as object characters. What is typed is read from the field as a change of its text and applied to the model (Enter starts a block, Backspace at the start of a list item or a quote takes it out first), and the field shows the model's text and styles again; code blocks are fields of plain text, and tables lay out their cells' fields in rows. List markers, checkboxes, quote lines, dividers, images and chips are drawn from the text's layout; an image's or a chip's object character is sized to reserve its box, so it stands in line with the text. A selection does not reach across a code block or a table, as each is a text field of its own.
- The editor reads only the open note's attachment folder, for its images, which are decoded off the main thread, turned as their EXIF orientation says, a GIF as its first frame and a large picture scaled down; nothing of a note is run, and it has no network access. Links in notes open outside the application only for `http`, `https` and `mailto`, as on the desktop.
- Links open through the application, and only when tapped in a read-only note or from the formatting bar's link actions: a note link naming a note identifier opens that note, a web or mail address the system's application, an attachment chip the file through a content address of a `FileProvider` limited to the libraries, the camera's photo folder and finished exports (a package the phone would install is offered for sharing instead). Text colours and highlights, tag colours and custom colours alike, are drawn in the shade of the palette as the desktop does (text mixed 65% with the text colour, highlights 28%, or 38% in dark palettes, over the page); numbered lists draw their markers counting items as the file nests them, so every numbering style and Multilevel look as on the desktop. Text follows the system font scale. Archived and trashed notes, and every note of a newer-format library, open in the same editor with editing off.
- Code blocks are highlighted as on the desktop: `core` interprets the syntax definitions of KDE SyntaxHighlighting 6.31 (its XML files, bundled unchanged with the definitions they include, each under the licence it names; Go and JSON are highlighted by definitions of the project's own in the same format, under its Apache License 2.0, and R Script is not bundled, as KDE's definitions for these three are licensed under the GPL, whose version 2 alone, for R, is incompatible with the Apache License; R code is shown as plain text, a deliberate difference from the desktop), in the styles of its themes: Breeze Light or Breeze Dark by light or dark mode, Monokai with the Monokai palette. The engine is a port of KDE SyntaxHighlighting's: line by line, contexts left open at a line's end carried to the next, the rules of the context on top tried in their order; the definitions' expressions are rewritten in Java's dialect, and the few that use recursion, which Java's expressions lack, leave their rule out. Languages keep the desktop's identifiers (the lower-case names of the definitions); a language not bundled is kept in the file and shown as plain text, and the language picker offers the desktop's list. Line numbers are drawn in a column beside the code, one per line on its first visual line; they are never text of the note.
- Fonts: a font family set on the desktop is kept and shown in the font when the phone has it, otherwise in the default font; the font picker lists the families available on the phone.
- The body codec is a port of the desktop's (`editor/HtmlCodec.cpp`) in `core`: a body is read into the model of the desktop's document (blocks, list membership by level, frames for code blocks and tables with a block before and after each) and written back from it with the desktop's writer, so a body the desktop wrote reads and writes back byte for byte, and a document the editor makes is written as the desktop would write it (an empty paragraph between two adjacent code blocks or tables, none before one that starts the note or after one that ends it). HTML pasted from other programs goes through the same reader in its paste mode, as on the desktop; HTML copied from a note is marked as such and pastes back in the note vocabulary. Round trips are tested with the fixtures (section 2) on the JVM.

### 5.2 Editing on a touch screen

- A formatting bar above the keyboard, scrollable, with groups: paragraph style; bold, italic, underline, strikethrough and more inline formats; text colour and highlight; lists (bulleted, numbered, checklist) with indent and outdent; insert (link, note link, image, attachment, table, code block, divider); undo and redo. A long press on a button explains it.
- Lists nest up to nine levels with their own types per level; tapping a checkbox toggles it. Numbered lists offer the numbering styles of the desktop.
- Tables: insert with a size, add and remove rows and columns, a header row, the table's width and column widths by dragging handles, cell content as on the desktop. A table's width is a percent of the text column but of no less than 40 body sizes, the desktop's text column in its default window, so on a phone a table is as wide as on the desktop and scrolls sideways within the note, with its handles, as a phone's column would leave its columns too narrow; exports draw it at the page's width.
- Code blocks: language picker, title, copy button, plain text editing.
- Images: the insert menu offers Take photo (the system camera writes the photo to a file of the application's cache folder offered through its `FileProvider`, so no camera permission is needed; the photo is stored as `IMG_<yyyyMMdd_HHmmss>.jpg`), Photo from gallery (the system photo picker, several at once; where the phone has none, the system document picker) and Image from file (the system document picker for images). A picked file that is not an accepted image is inserted as an attachment, as on the desktop. Several files are inserted at the cursor separated by spaces.
- Tapping an image in an editable note selects it, and the formatting bar leads with its actions: Show full screen, Image size (Small 25 %, Medium 50 %, Large 75 %, Full width; a width set on the desktop between them is kept and marks none), Wrap text (In line with text, Square, Top and bottom, each with its glyph; Square makes a full-width image Medium) and Remove image; each change is one undo step. An image wrapped Square stands at the left of the text column, or of its table cell, from the top of the line its character is on, and the text, list markers and quote lines flow along its right side and continue below it at the full width, as on the desktop; the image keeps 0.75 rem of room on its right and below it, and an image whose top would fall beside an earlier one starts below it. The lines beside the image are moved right by ending the paragraph's style where the image's band starts and where it ends, found by measuring the text, so the body is not changed. An image that leaves less than four body sizes of room beside it stands on a line of its own, as one wrapped Top and bottom does. The selected image also shows handles at its corners, as on the desktop: dragging one sets its width from 10 % to full width, with an outline of the size it takes while dragging, taking 25, 50, 75 or 100 % when within 3 % of them, never larger than the image itself; the width is stored when the finger lifts, as one undo step. The system's selection handles and highlight of the image's character are drawn transparent, as the outline shows the selection; touches below the image's line still reach those handles, so the image's handles take touches only above it, and at the edges of the screen they are excluded from the system's back gesture. The file keeps any width the desktop wrote until it is changed. A long press on an image or an attachment chip in an editable note picks it up and selects it, and a drag moves it within the note, as a plain drag does on the desktop: a line shows where it goes, at a place in the text outside code blocks, table cells included; near the top or the bottom edge the note scrolls, once the finger has moved. Lifting the finger moves it there as one undo step, keeping its file, width and wrapping, and it stays selected; a place beside it, on a divider or outside the text moves nothing. A tap without the long press selects it, and a drag before the long press scrolls the note. In a read-only note a tap opens the image full screen. The full-screen viewer is the design system's gallery viewer: the note's images in body order, each file once, fitted on black and turned as their EXIF orientation says, a GIF as its first frame; its menu has Open in another app and Share.
- Attachments: Attachment in the insert menu inserts any files through the system document picker. A chip shows the file type's glyph (chosen by the extension, as the desktop chooses it by the file's type), its name and size. A selected chip leads the formatting bar with Open attachment, Share, Save as… (a copy through the system's document picker) and Remove attachment; in a read-only note a tap opens it. Opening goes through a content URI granting that one file to the application the system chooses; an Android package, recognised by its extension or by its content (a ZIP archive holding `AndroidManifest.xml` or packages), is never opened, only offered for sharing. Attachments are not renamed, as on the desktop, which dropped its Rename: it was the only editor action that changed a file outside the body and tied the undo history to the file system.
- Size limits and accepted image kinds are those of the desktop (section 3.5): files over 50 MB are not added, and a PNG, GIF or WebP of more than 8192 × 8192 pixels becomes an attachment; a file that is not added is named in a transient message. Files are stored off the main thread under their names, made safe and unique as on the desktop (`photo (2).jpg`): the data goes to a temporary file in the library's `attachments` folder, beside the note folders, where sync does not look, is flushed and renamed into the note's folder; a sync run downloads an attachment the same way, so a file left by a crash never lies in a note's folder, where sync would upload it; temporary files an insertion or a download left when the system stopped it are removed when the application next starts, once they are an hour old, as a run may still be writing one.
- Pasting: a picture of the clipboard and a picture in a `data:` address of pasted HTML are stored as `Pasted image.<kind>` (the name in the interface language) when they are an accepted image of at most 50 MB, and are left out otherwise; pictures of `file:` addresses are left out, as the editor has no file access. Images and chips copied from another note of the library are copied into this note's folder, so no note depends on another one's (desktop specification section 3.5). Until a pasted object is stored, it holds its place, writes nothing into the body and is not an undo step of its own.
- Markdown shortcuts and paste cleaning as on the desktop; find in the note from its menu, without Replace. A tap on the empty room below the text puts the cursor at the end of the note and opens the keyboard.
- The note is saved one second after typing stops, when another note opens and when the application goes to the background. A rotation keeps the cursor: the screen keeps the selection as two positions of the whole document in its saved state, and the new editor restores it, kept inside the note, with the focus when the body had it. Undo keeps whole states; typing of one kind within half a second is one step, and undo right after a Markdown shortcut brings back what was typed. A change of the note's file by a sync run follows the desktop's rule: without unsaved changes the note reloads in place; with unsaved changes the synchronised version is kept and the local text becomes a conflict copy (desktop specification section 3.7).
- With a hardware keyboard, the desktop's shortcuts apply where the action exists on Android.

## 6. Export

File names, the HTML format, the look of drawn notes, the ZIP packing of several files and the limits of JPG parts are those of the desktop; this section names what differs on a phone.

- Export is in the note menu and the selection bar, also for archived notes; notes in the trash are not exported. In a newer-format library, which is read-only, a note is exported from its menu only: the design system's selection bar always has the favourite toggle, which such a library cannot change.
- The form dialog chooses the format, PDF, HTML or JPG, and for PDF the page size: A4 or Letter, starting with Letter where the phone's region uses it, as on the desktop. What was just typed in an open note is saved first, and a note that cannot be saved is not exported.
- **PDF** is written by Android's `PdfDocument`, one file per note, several notes in a ZIP, as on the desktop: the note drawn as the editor draws it, in the light Warm palette, with the title and the updated date above the text, on pages of the chosen size with margins of 20 mm and the interface's sizes at 96 pixels per inch, a line never crossing a page. Links are drawn as links without a target, web links too, as `PdfDocument` has no links.
- Exports run in the application's scope with their progress in the dialog, so a rotation keeps them. Cancel stops a running export and keeps the dialog open. A finished export offers Save, through the system's document picker, and Share, through the share sheet. Cancel then discards it, and a saved export closes the dialog with a confirmation. A failure is shown in the dialog with the choices kept. The application keeps no copy: the temporary file lives in `cache/export/`, which the `FileProvider` offers for sharing, until the dialog closes or the application next starts. An export runs without a foreground service; if the system ends the application, it is started again.
- PDF and JPG are drawn by the editor's own drawing of the note, laid out on the page's or the image's column; JPG into a bitmap. The size of drawn text does not follow the system font scale, as the export is not for this device's screen. A note with more images than fit in memory as one HTML document or one image shows the failure in the dialog; a picture too large to decode is drawn as its place.

## 7. Synchronisation

The model is that of the desktop specification section 12: one sync storage per library, the remote lock, sync state, three-way merges, tombstones, conflict copies and the first-connection rules. The sync storage is a folder on an SFTP server.

### 7.1 Connection

- A connection has a host, a port (22 by default), a user name, the remote folder and a sign-in method: a password or a key. Browse lists the folders on the server, says whether a folder holds a Jotter library, is empty or holds other files, and creates folders, as on the desktop.
- Keys: the person generates an Ed25519 key on the phone (stored in OpenSSH's format), and the public key is shown in a framed block, with Generate key, Import key and the icons Share and Copy in one row below it, to add it to the server's `authorized_keys`; or imports a private key file (OpenSSH, PEM or PuTTY), with its passphrase when it has one, which is checked on import. A connection being changed keeps its stored key until another is chosen. A password also answers keyboard-interactive sign-in, once.
- Host keys are checked against Jotter's own list on the phone (`no_backup/known_hosts`, OpenSSH's line format, one key per host). An unknown key shows its type and SHA256 fingerprint and is trusted only when the person accepts it; a changed key, including a key of another type than the recorded one, stops synchronisation, and the Sync tab of Settings shows the recorded and the new fingerprint and trusts the new key on request. A key the person accepted is recorded on the next connection only when the server still presents the same fingerprint.
- Saving a connection first checks it: connect, verify the host key, sign in, write and remove a probe file through a temporary file and a rename, and check that the folder holds this library or nothing (desktop specification section 12.6). The lock is created exclusively (`SSH_FXF_EXCL`), as on the desktop, and an upload replaces its target through `posix-rename@openssh.com` when the server offers it, otherwise through the plain rename, which servers without the extension, such as SFTPGo, perform replacing the target; OpenSSH and SFTPGo (on a local disk; its cloud storages copy on a rename, which is not atomic) both serve. A failed check saves nothing and names the step that failed. Changing the connection to another folder clears the sync state, so the next run is a first connection. The SSH library is recorded in section 9.
- Disconnect removes the library's connection, credentials and sync state; the files stay on both sides.

### 7.2 Credentials

- Passwords, key passphrases and private keys are encrypted with an AES-GCM key generated in the Android Keystore, which never leaves it, and stored in the application's no-backup storage, one file per library (`no_backup/credentials/<library-id>.bin`). A file that cannot be decrypted reads as no secret, and the next run asks for the sign-in again.
- Secrets are never shown again or prefilled; a public key is shown, a private key is not.

### 7.3 Sync runs

- Runs follow the desktop's algorithm exactly: the lock in the remote folder, the comparison with sync state, uploads through a temporary file and a rename, the time precision rules, merges and conflict copies (desktop specification sections 12.2 to 12.4). A device of either kind must be able to sync with a folder another device of either kind synced last. A file name in a remote attachment folder that would leave the folder (`/`, `\`, `.`, `..`), which only a damaged or hostile server lists, is ignored.
- A run is started when the application starts or returns to the foreground, 30 seconds after the last change while the application is open, on pull to refresh in a note list and on Sync now, and in the background at the chosen interval (Off, 15, 30 or 60 minutes; 15 by default, Android's shortest period) through WorkManager.
- On a metered network (mobile data, a hotspot or another network Android counts as metered; no network counts as metered too) runs do what the person chose for the library: Everything (the default); Text only, where notes and the library's files synchronise but attachments new or changed on the server are not read, are left for a run on an unmetered network and are listed again by it, while local attachments are still uploaded; or Wait for Wi-Fi, where runs the application starts by itself wait for an unmetered network and the interval's periodic work requires one. A run left on a metered network, or one that left attachments, asks for one-time work on an unmetered network. Sync now, Retry and pull to refresh run on any network, moving only text unless Everything is chosen. Attachments left for Wi-Fi are told by a notice on the Sync tab; a note shows a missing attachment as it shows any missing file until it arrives. This is a device's choice of when to read files and does not change the desktop's sync model: a deferred attachment is never recorded in the sync state, so its absence is not taken for a deletion.
- Synchronisation can be paused for an hour, one, three or seven days, until the start of a day chosen in a calendar, or until the person resumes it. While paused, no run the application starts by itself does anything (at start, after a change, at the interval, retries and runs waiting for Wi-Fi); Sync now, Retry and pull to refresh still run and the pause stays. Changes wait on the phone. A pause ending while the application runs starts a run; otherwise the next ordinary run synchronises. Resuming by hand starts a run at once.
- Every run goes through WorkManager: the application's requests as expedited one-time work, queued behind a running run (one more run follows it when it was requested meanwhile), and the interval's runs as periodic work with the network constraint. A run that has started finishes even when the application goes to the background; a run lasting more than three seconds becomes a foreground service of type data sync with the ongoing sync notification that Android requires for it (Android may refuse that to a background start; the run then goes on as ordinary work). Network failures are retried after 1, 2, 4 and more minutes up to the interval, or 15 minutes without one; a lock held by another device is tried again after 30 seconds. A library downloaded or connected anew synchronises at once.
- Network failures are retried with growing pauses; sign-in and host key errors wait for the person. While a run waits or failed, a status banner under the top bar says so and opens the Sync tab of Settings.
- Conflict copies a run made are announced in a snackbar that opens the first conflicting note. A conflict copy is self-contained: its images and attachments are duplicated into `attachments/<copy-id>/` and its addresses rewritten, the source files stay, and the files reach the storage before the note naming them. A source file that is missing or unreadable stops the run before the local version is replaced.
- Local steps are short transactions: a run and the application compare and replace a library file under one lock of the process, never held across a network call or a database call. The editor replaces a note only when its file is still the version it read; `library.json`, `collections.json` and `rules.json` are changed by applying each edit to the file as it is on disk, so downloaded tombstones, favourites, tag colours, settings and entries stay. This gives the outcome of the desktop's merge against the last-read version without keeping that version, since every edit here is applied within such a transaction.
- A run renews its lock (ten minutes, renewed at half of that) between steps of long listings and transfers, on the storage's own thread, as well as between files; a lost lock stops the run. A run that left files changed locally during the run is partial: it keeps the time of the last full success, shows the deferred state and is repeated at most three times after five seconds. A version that cannot be read for a merge is a visible error needing repair, with no automatic retries.
- A run that fails with a sign-in or host key error while the application is not visible shows one notification, which opens the Sync tab of Settings and is removed when a run succeeds; other failures are only shown in the application. A pulled refresh is confirmed in a snackbar, a failed one with Retry.

### 7.4 First start and another device

- The first start and the Sync tab of Settings offer Download from SFTP: the connection as in section 7.1 (the folder must hold a library that is not on the phone yet), then the library is downloaded into a temporary folder with a temporary sync state, both published only after a complete download and only into a missing or empty folder, and opens already connected. A failed attempt removes only its own data and can be tried again.
- Connecting an existing library to a remote folder follows the desktop's first-connection rules (desktop specification section 12.6): an empty folder receives the library, a folder with the same library is merged with an empty base, and a folder with another library or other files is refused.

## 8. Interface

### 8.1 Screens

- **Home screen:** what the application opens with, in place of a bottom bar. The top bar has the name, the search button (all notes) and the Settings button. Below it, in one scrolling list: All notes, Unfiled notes, Favourites, Archive and Trash; then Collections with its + creating a top-level collection; then Tags with the number of tags, folded by default, unfolded by tapping its header. The round Add button creates a note. A connected library synchronises on pull to refresh, and the status banners show under the top bar. Expanded nodes and the unfolded tags survive rotation and being covered by another screen.
- **Collections and tags:** the collection tree in the stored order, each row at least a touch target high with the expand toggle at the start (a space for a collection without children), the collection's glyph (`Folder` by default) and its name in its colour, and the number of its active notes with its descendants'. The tag tree goes by the parts of the paths, so `work/urgent` lies under `work` even when no note has `work` itself; parts compare case-folded and keep the spelling of their first use; each row shows the tag glyph and the last part in the tag's colour (its own or its nearest coloured parent's) and the number of active notes with the tag or its children. Tapping a row opens its note list.
- **Note lists:** All notes, Unfiled notes, Favourites, Archive, Trash, a collection's notes (with its descendants') and a tag's notes (titled with the whole path) are subordinate screens: Back, the title, the search button and, in the trash while it holds notes, ⋮ with Empty trash. A row above the notes chooses the order (a sort chip opening a choice dialog and the direction toggle), beside a collection's Only its own notes; Favourites have no such row, as they keep the stored order of `library.json`, with the favourite collections leading as the same rows as in the tree. The round Add button creates a note in the list's context, except in the archive and the trash, whose empty state names the trash retention. While synchronisation waits for another device or failed, the lists show a status banner under the top bar that opens the Sync tab of Settings; a connected library's lists synchronise on pull to refresh. A list keeps its scroll position and its search while a note or Settings covers it.
- **Search window:** a window over the list, near the top of the screen and above the keyboard, that takes the focus when nothing is typed yet; tapping outside or Back closes it and keeps the query and the filters. The filter toggle beside the field opens the filters, which wrap so that all of them fit the width of the screen. A result opens its note, and Back from the note returns to the results; in a wide window the note opens in its pane, with the window closed until the note is.
- **Note:** a detail screen with a top bar of Back, the title edited in place ("Untitled" when empty) and ⋮; under the title, on a smaller line, the note's collections ("Unfiled" without any) and, after the tag glyph, its tags in their colours, scrolling sideways, or without any the word Tags and +. Tapping the collections opens the Collections dialog, and tapping the tags a popup 240 dp wide under the line: the note's tags with × removing each at once, a focused field adding the typed tag with the keyboard's Done and staying ready for the next (a tag the library has in another case takes the library's spelling), and up to eight tags of the library that match, those starting with the text first, added by tapping them. Tapping outside it or Back closes it; a note that cannot be edited shows the line without them, and without its tag glyph, word and + when it has no tags. The line stands over the top of the editor, which leaves it room above the text, and scrolls away with the text, also while typing; Back, the title and ⋮ stay. An empty body of an editable note shows the hint Start writing… in the palette's `outline` role, paler than the text, until its first character, also with a title; the hint is not stored. Below the top bar come a banner for a note in the archive or the trash or in a newer-format library, and the entries of ⋮ (Information, Favourite, Icon, Colour, Find, Add location while geotags are on and the note has none, Export, Archive, Move to trash last; Unarchive for an archived note; Restore and Delete permanently for a trashed one); the editor fills it, the formatting bar sits above the keyboard.
- **Settings:** the preferences template as a full-screen window: the title and × at the top, then tabs with their glyphs (a scrollable tab row, which has room for more), each a column of sections. × or Back returns to where it was opened from, with that screen as it was; screens below Settings have Back. It opens from the home screen, and at the Sync tab from the status banners and notifications. **General:** Appearance (theme picker, light or dark, language), Notes (add location to new notes, section 4), and an About row opening the version, Licences (the components with their licences, each opening the licence's text) and Privacy policy, which opens `PRIVACY.md` of the repository in the browser (a snackbar says so when the phone has no browser), as Google Play requires a link to the policy inside the application. **Library:** a row naming the open library with when it last changed, opening the Libraries screen; the note count with the archive and the trash; a sentence saying the library exists only on this phone while it is not connected; Problems while there are any, a subordinate screen listing each unreadable note file with its reason in the interface language and its technical detail, and Create normalised copy and Delete original for a body outside the vocabulary (section 2); trash retention of 7, 30 or 90 days or until the trash is emptied, a setting of the library written to `library.json`, shown as a plain value in a newer-format library; Rules, a row with the number of rules. **Sync:** see below. Checked checklist items are always struck through and muted, the desktop's on-by-default preference not being offered on a phone; the file does not depend on it. There is no notifications section: the permission is asked at the first start (section 9) and the channels are in the system's settings of the application.
- **Libraries:** a subordinate screen of the Library tab listing the libraries of the device, the most recently changed first, each with its name and, smaller, when a note of it last changed (the newest updated time in its index, or its creation time while it has no notes). The library format gives a library no name and its local folder is only an identifier, so a connected library is named after the last part of its remote folder (after the server for the home folder), and any other is called Library on this phone. The open library carries a check and tapping another opens it. The round Add button creates a library and opens it; ⋮ holds Rebuild index; Delete library from this phone comes last, confirmed with the note count, and also removes its connection, credentials and sync state, after which another library of the device opens or the first start shows.
- **Sync tab:** built as the integrations template's service screen for the SFTP storage: last sync, status, a notice explaining an error with its action (Retry, Change sign-in for a refused sign-in, Trust for a changed host key after showing both fingerprints), the server, the folder, the sign-in method and, for a key, the public key with Copy and Share, Change sign-in, Sync now, the log of the five most recent runs (the time and a summary of files uploaded, downloaded and merged and conflict copies made, or the failure in the error colour), when to synchronise (interval, mobile network, pause), Download from SFTP and Disconnect last. A pause shows as a warning notice with Resume and a warning mark in the diagram, attachments left for Wi-Fi as an information notice. Without a connection: an explanation, Connect, opening the setup screen with the connection fields, Browse, the key generation or import, and Check and save, and Download from SFTP. Browse is a dialog that signs in and lists the folders from the folder typed in or the home folder, with Up, whether the shown folder holds a Jotter library, is empty or holds other files, New folder and Choose.
- **First start:** the connection template's centred column: the logo and name, a sentence saying the library exists only on this phone until a sync storage is connected, Create library (with an inline error when it fails), Download from SFTP and the interface language below. A created library replaces the screen with the home screen; Back does not return to it. While the library opens a loading state shows, and a library that cannot be opened shows an error state with Retry; a remembered library whose folder is gone returns to the first start.
- **Wide windows:** at least 840 dp wide the list and the open note are shown side by side (list and detail), as the desktop's panes: a note opened from a list lies on top of it in the navigation stack and shows in a pane beside it (the list takes two fifths), a row tapped there replaces it, Back closes it; in a narrow window the same stack shows the note full screen, so rotating keeps the open note.
- Both orientations are supported; rotating keeps the open screen, the open note, the cursor and drafts.
- A library of a newer format shows a status banner on the home screen saying it was written by a newer Jotter and asking to update the application.
- Every state is designed, as on the desktop: an empty library, an empty collection, tag or view, no matches, an empty archive and trash, a read-only (archived, trashed or newer-format) note.

### 8.2 Appearance

- **Palettes:** Warm (default), GitHub, GitHub Dimmed and Monokai, the desktop's palettes with the same role values; Monokai is stored as `monokai`. The theme picker shows each palette in its own colours.
- **Light or dark:** System, Light or Dark; GitHub Dimmed and Monokai are dark only and disable the choice with the reason.
- **Text size** follows the system font scale; there is no interface size setting as on the desktop.
- Appearance is a device preference in DataStore and the language the platform's per-application language (section 8.4); library settings (trash retention, rules) live in the library and follow it to other devices, as on the desktop.

### 8.3 Notifications

- Two channels with localized names: Synchronisation (the ongoing notification of a long run, low importance) and Sync problems (the sign-in or host key error of a background run).
- The ongoing notification is removed when its run ends, also when Android refused the run a foreground service and it was posted as an ordinary notification.
- Notifications follow the design system's widgets and notifications rules: the accent is the palette's primary colour, the small icon a monochrome glyph, the text in the language chosen in the application. Tapping one opens the Sync tab of Settings.

### 8.4 Language and accessibility

- Interface text comes from Android string resources in English and Russian; the language follows the system or the choice in Settings. It is the platform's per-application language, kept by `LocaleManager`: the system's settings of the application offer the same choice and change the same value, so neither overrides the other, and the generated table of contents, notifications and conflict copies use it too.
- Every action is reachable with TalkBack and a hardware keyboard; touch targets follow the design system.
- Screens are covered by a screenshot test (Roborazzi) in light English, dark Russian, large text and the Monokai palette.

## 9. Platform and distribution

- Application ID and package `io.github.nir0k.jotter`.
- Android 16 (API 36) and newer, so the application relies on the platform's current behaviour without branches for older versions; the newest stable SDK as the target (API 37 when the project is created).
- Kotlin, Jetpack Compose and Material 3; Gradle with Kotlin scripts, a version catalog and convention plugins in `build-logic`; modules: `core` (library format, body codec and editing model, code highlighting, index, search, rules, sync engine; plain Kotlin where possible, so it is tested on the JVM), `designsystem` (the interface's theme, components and glyphs), `editor` (the native editor and the drawing of notes for exports), `data` (the Android side of the library: the open library, preferences, background sync, notifications, credentials, geotags, exports), `ui` (what the feature screens share), the feature modules `feature:notes`, `feature:note`, `feature:settings` and `feature:sync`, which depend on `ui` and `data` but not on each other, and `app` (the activities, navigation and capture).
- Dependencies are open source, published outside Google's proprietary SDKs, and pinned exactly.
- The syntax definitions and the three themes of KDE SyntaxHighlighting 6.31 are resources of `core` (`syntax/`), with an index of the definitions' names; they are read with the platform's XML parser once their document type's entities are replaced, and the themes with `kotlinx-serialization-json`. The editor needs no other library: Compose's text fields with their input and output transformations, `contentReceiver` for pastes and the platform's `ImageDecoder` and `PdfDocument`.
- SFTP goes through sshj (`com.hierynomus:sshj`, Apache 2.0, with SLF4J and ASN.1 One): plain Java, so the sync engine and the SFTP storage live in `core` and are tested on the JVM; it opens files with `SSH_FXF_EXCL`, renames through `posix-rename@openssh.com` when the server offers it, and reads OpenSSH, PEM and PuTTY keys. Bouncy Castle (`org.bouncycastle:bcprov-jdk18on` and `bcpkix-jdk18on`, MIT), which sshj depends on, gives it Ed25519 signatures and X25519 key exchange and writes the keys generated on the phone in OpenSSH's format; it is registered as the `BC` provider in place of Android's reduced one, which lacks these algorithms. The release build keeps only the provider's algorithm families sshj asks it for (the digests and HMACs, AES, ChaCha20 with Poly1305, Triple DES, Blowfish, and the DH, DSA, EC, EdDSA and RSA keys; key files are decrypted by the platform's providers), so R8 removes the rest of Bouncy Castle's provider classes; the other ciphers sshj knows are disabled when it starts. sshj sends each write of a file as one request, so uploads go in pieces of the channel's packet size. JSch was not chosen, as it offers no exclusive creation, so its lock would need `hardlink@openssh.com`, which SFTPGo lacks; nor was Apache MINA SSHD, which is larger. Background runs and the foreground service of long runs go through WorkManager (`androidx.work`).
- The index uses `androidx.sqlite:sqlite-bundled` (SQLite with FTS5) and the Snowball stemmers for English and Russian as generated Java, vendored in `core` with their BSD licence; the Snowball release is the newest one, which may stem a few English words differently from the desktop's libstemmer, as each device's index is its own (section 3). The APK carries the bundled SQLite for `arm64-v8a`, `armeabi-v7a` and `x86_64`; 32-bit `x86` is left out, as no Android 16 device runs on it.
- Library files are read with `kotlinx-serialization-json` as JSON trees and written by `core`'s own writer, which reproduces the output of Qt's JSON writer that the desktop uses: keys in alphabetical order, two-space indentation, empty arrays and objects on two lines, Qt's string escaping and number forms (integral values up to 2^53 as integers, other numbers with the fewest digits that read back, in the shorter of the decimal and exponent forms). The fixtures and unit tests with values produced by Qt check it.
- Permissions: Internet; notifications (asked at the first start, as background runs report sign-in and host key problems in a notification, and again on the next start after a background run could not report one); location, precise and approximate together (asked only when geotags are switched on); the foreground service of type data sync for long sync runs. No camera or storage permission: photos come through the system camera, writing to a file of the cache folder that the `FileProvider` offers (`cache/camera/`, beside the libraries it offers for opening attachments and the finished exports it offers for sharing), and files through the system's pickers. The capture screen receives shared content through an exported activity filtering `SEND` and `SEND_MULTIPLE` of any type, and the Quick Settings tile is a `TileService` bound with `BIND_QUICK_SETTINGS_TILE`; neither needs a permission of the application.
- The version comes from the root `VERSION` file: `versionName` is its value and `versionCode` is `major * 1000000 + minor * 1000 + patch`.
- Releases are signed APKs attached to GitHub releases. Signing reads `keystore.properties` or `JOTTER_ANDROID_` environment variables; the keystore is never committed.
- The application icon is drawn from `docs/assets/icon.png`: an adaptive icon with the drawing as the foreground, inset to the safe zone, on a light background (`#EAF2FC`) that is dark in the phone's dark theme (`#1D232A`, the Warm palette's dark card colour); the New note shortcut shares the background, its glyph in the Warm palette's primary colour of the same variant. Whether a launcher follows the dark variant is its own choice. It has no monochrome layer: with themed icons, earlier Android versions show the coloured icon and Android 16 QPR 2 and newer tint it themselves. The licences of third-party components (Bootstrap Icons, KDE SyntaxHighlighting's definitions and themes and the other bundled libraries) are listed in About, in the General tab of Settings. The interface's own glyphs are part of this project, under its licence, and are not listed; nor is SQLite, which is in the public domain. The list follows the release build after R8 has removed the unused code: dependencies it removes entirely (Okio, atomicfu, JSpecify) are not listed, and Protocol Buffers, which DataStore carries inside, is.

## 10. Testing

- The fixtures (section 2): reading and writing every note form back unchanged, in `core`, through the library format and through the body codec of the editor.
- The editor's commands on the model: typing, Enter and Backspace, lists and their nesting, formats and links, shortcuts, code blocks, tables, find, pasting and the selection kept on rotation; the highlighter with every offered language.
- The merge cases of the fixtures (section 2), merged by the engine's own merge of a file.
- The merges, deletions, first connection and lock scenarios of the desktop's sync tests, run against a local folder in unit tests and against an SFTP server on request, such as the OpenSSH test stand of [Jotter](https://github.com/nir0k/Jotter/tree/main/tests) or an SFTPGo container: `JOTTER_ANDROID_SFTP=sftp://jotter:jotter@127.0.0.1:2222/library` runs the same scenarios there, each in a folder of its own, with the checks of host keys, sign-in errors, the probe and choosing a folder, and the transfer of an attachment of the largest accepted size, which only SFTP sends in pieces; `JOTTER_ANDROID_SFTP_KEY` names a private key the stand accepts, for the key sign-in. The encrypted key of the passphrase check is made by `ssh-keygen` for the run, so the repository holds no private key.
- The open note following its file and being left (an outside change reloading it or keeping unsaved text as a conflict copy, an empty note discarded), when a requested run goes and what it moves, the pauses before retries, and the host key check without a server.
- Screenshot tests of the screens (section 8.4), including Monokai in dark mode, and of the design system's icon and colour pickers.
